## 1. 概述

### 一句話說明

技術債管理橫跨 6 個指令，形成「登記 → 追蹤 → 標註 → 結案 → 驗證」的完整閉環，所有操作嵌入既有 SDD 流程，不需學習額外指令。

### 設計原則

| 原則 | 說明 |
|------|------|
| **嵌入式設計** | TD 操作嵌入既有指令流程，不新增獨立指令 |
| **人機協作** | 自動偵測 + 人工確認，避免誤登記或誤結案 |
| **只進不出防線** | 即使「忘記標註 TD Ref」，unify-flow 的附帶解決偵測仍可補捉 |
| **向後相容** | 新增欄位皆為選填，既有 TD Registry 無需遷移 |

## 2. TD Registry 資料結構

### 檔案位置

```
docs/technical-debt.md
```

### 核心欄位

每個 TD 項目包含以下欄位：

| 欄位 | 必填 | 說明 |
|------|------|------|
| `Priority` | ✅ | P1（緊急）/ P2（排程）/ P3（待改善） |
| `Status` | ✅ | Open / In Progress / Resolved / Won't Fix |
| `Resolved-By` | 結案時 | `Feature-NNN US XX-N`（解決此 TD 的 Feature 與 US） |
| `Resolved-Date` | 結案時 | YYYY-MM-DD |
| `Won't-Fix-Reason` | Won't Fix 時 | 決策理由說明 |
| `Type` | ✅ | test-regression / code-quality / env-issue / bug / design-debt / security |
| `Source` | ✅ | code-check / pr-review / refine-loop / system-health / manual |
| `Component` | ✅ | 受影響的主要模組（如 auth / cli / db） |
| `Dedup-Key` | ✅ | `{type}:{primary-affected-path-or-module}` |
| `Detection-Count` | ✅ | 偵測次數（去重時累加） |

### Severity ↔ Priority 對照

| 來源 | 嚴重性用語 | TD Priority | 說明 |
|------|------------|-------------|------|
| code-check | E1 HIGH（阻斷） | **不進 TD** | MUST 當場修復 |
| code-check | E2 LOW | P3 | 非功能性瑕疵 |
| code-check | E3 DEFERRED | P2 | 跨 Feature，需排程 |
| pr-review | CRITICAL / HIGH | **不進 TD** | MUST 當場修復 |
| pr-review | MEDIUM（降級） | P2 | 經評估後延遲 |
| pr-review | LOW（放行） | P3 | 成本過高 |
| system-health | Hard Fail | P1 | 阻斷性品質問題 |
| system-health | Score < 60 維度 | P2 | 趨勢惡化 |
| system-health | Score ≥ 60 維度 | P3 | 待改善 |

### 去重規則

新增 TD 前 MUST 檢查是否已有相同 `Dedup-Key` 的 Open / In Progress 項目。若已存在，更新 `Last-Detected` 和 `Detection-Count`，不新增。

### 老化升級規則

| 未處理 Milestone 數 | 行動 |
|---------------------|------|
| ≤ 2 | 維持原 Priority |
| 3 | P3 → 升級為 P2，system-health 報告特別標記 |
| ≥ 4 | P2 → 升級為 P1，MUST 排程或轉 Won't Fix |

### 狀態轉換

```
建立 → Open → In Progress → Resolved（經 unify-flow 確認）
                  │

                  └─→ Deferred（跨 Milestone 延遲，回到 Open 重新評估）
```

## 4. 登記通道（建立 TD）

### 4.1 flowkit.system-health

- **觸發**：執行全專案健康檢查時
- **操作**：Register + Dedup
- **Priority 來源**：依 Hard Fail / Score 分級

### 4.2 flowkit.code-check

- **觸發**：靜態分析發現跨 Feature 問題（E3 DEFERRED）或非功能性瑕疵（E2 LOW）
- **操作**：Register + Dedup
- **Priority 來源**：E2 → P3, E3 → P2

### 4.3 flowkit.pr-review (Phase 7.5)

- **觸發**：品質審查中 LOW 層級問題被判定為「成本過高不修正」時
- **操作**：Register + Dedup
- **Priority 來源**：LOW → P3, MEDIUM 降級 → P2

### 4.4 flowkit.refine-loop

- **觸發**：修正 Bug 過程中發現關聯問題
- **操作**：Register + Dedup

### 4.5 手動登記

- **觸發**：任何來源的人工判斷
- **操作**：直接編輯 `docs/technical-debt.md`

## 5. 追蹤與規劃（讀取 TD）

### 5.1 flowkit.BDD-Milestone (Read-only)

- **觸發**：規劃 Milestone 時
- **操作**：讀取 Active Items 中的 `Milestone-Candidate: true` 項目
- **目的**：建議將高優先級 TD 納入 Milestone 的 User Story

> 此指令不做修改，僅讀取並建議。

## 6. 結案通道（關閉 TD）

### 6.1 speckit.specify — TD Ref 標註（前置準備）

**時機**：撰寫 Feature Spec 時

當 Feature 的某個 US 與現有 Open TD 相關時，specify 會在 US 標題下方標註：

```markdown
### US A-1: 修正上傳檔名安全性問題
> TD Ref: TD-001

**As a** 系統管理者
**I want** ...
```

**適用範圍**：所有 Feature（含 bugfix、enhancement、new feature），不限於 Bugfix Milestone。

**強度等級**：SHOULD（非阻擋）

### 6.2 flowkit.unify-flow — TD Reconciliation（主要結案點）

**時機**：Feature 完成 Unify Flow 時（Phase 7）

**流程**：

1. 讀取 `docs/technical-debt.md` 中所有 Open / In Progress TD
2. 讀取 Feature `spec.md` 中所有 `> TD Ref: TD-XXX` 標註
3. 產出候選結案清單：
   - **直接解決**：有 TD Ref 標註 → 建議 Resolved
   - **附帶解決偵測**：git diff 涉及 TD Component 但無 TD Ref → 提示確認
4. **MUST ASK 人類確認**每一項結案決定
5. 確認後更新 `docs/technical-debt.md`：
   - Status → Resolved / Won't Fix
   - 填入 `Resolved-By`、`Resolved-Date`
   - Won't Fix 填入 `Won't-Fix-Reason`
   - 從 Active Items 表移至 Resolved 表

**強度等級**：SHOULD（TD Registry 不存在或無 Open 項目時自動跳過）

## 7. 驗證閘門（確認一致性）

### 7.1 flowkit.pr-review — TD Closure Verification

**時機**：PR Review 時（Phase 7.6），僅 Feature 分支合併時執行（非 hotfix）

**驗證邏輯**：

| 類型 | 檢查條件 | 輸出 |
|------|----------|------|
| 正向驗證 | Feature spec 有 TD Ref 但 TD 仍為 Open | ⚠️ WARNING |
| 反向驗證 | PR diff 涉及 Open TD 的 Component 但未結案 | ℹ️ INFO |

**強度等級**：SHOULD（不阻擋 PR Review 完成）

## 8. TD Touch Point Matrix

綜合所有指令對 TD 的操作一覽：

| 指令 | Read TD | Register | Dedup | Close | Verify | 備註 |
|------|---------|----------|-------|-------|--------|------|
| `system-health` | ✅ | ✅ | ✅ | — | — | 環境與依賴掃描 |
| `code-check` | ✅ | ✅ | ✅ | — | — | 靜態分析 E2/E3 轉 TD |
| `pr-review` | ✅ | ✅ | ✅ | — | ✅ | LOW 放行轉 TD + 結案驗證 |
| `BDD-Milestone` | ✅ | — | — | — | — | 讀取建議納入 Milestone |
| `specify` | ✅ | — | — | — | — | 標註 TD Ref |
| `unify-flow` | ✅ | — | — | ✅ | — | TD Reconciliation 結案 |
| `refine-loop` | ✅ | ✅ | ✅ | — | — | 修正中發現關聯問題 |

> 其他指令（plan、tasks、analyze、implement、checklist、trace 等）不涉及 TD 操作。

## 9. 操作範例

### 9.1 典型流程：Bugfix Feature 解決多個 TD

```
1. BDD-Milestone: 規劃 Milestone，將 P1/P2 TD 納入 US
   ↓
2. specify: 撰寫 Feature Spec，每個 US 標註 > TD Ref: TD-XXX
   ↓
3. implement: 實際修復程式碼
   ↓
4. unify-flow Phase 7: 
   - 自動比對 TD Ref → 產出候選結案清單
   - ASK 人類確認 → 更新 technical-debt.md
   ↓
5. pr-review Phase 7.6:
   - 驗證所有 TD Ref 的 TD 已結案 → ✅
```

### 9.2 附帶解決場景

```
1. specify: Feature 主要目的是新功能，未標註 TD Ref
2. implement: 順便重構了某個模組
3. unify-flow Phase 7:
   - git diff 偵測到修改了 TD-003 的 Component 
   - 提示：「TD-003 的 Component 在此 Feature 中有變更，是否已解決？」
   - 人類確認 → 結案
```

### 9.3 Won't Fix 場景

```
1. unify-flow Phase 7:
   - TD-010 與 Feature 的 US 有關，但無法解決（外部套件限制）
   - 人類決定：Won't Fix
   - 填入 Won't-Fix-Reason: "moviepy 依賴 pillow<12.0，無法升級"
```

## 10. 常見問題 FAQ

### Q：忘記在 specify 標註 TD Ref 怎麼辦？

不影響結案流程。`unify-flow` 的**附帶解決偵測**會透過 git diff 比對 Open TD 的 Component，即使沒有 TD Ref 標註，只要修改了相關檔案就會提示確認。

### Q：TD 只能在 unify-flow 結案嗎？

是的，`unify-flow` 是唯一的結案通道。這確保：
1. 結案發生在 Feature 完成（System Spec 已合併）之後
2. 每次結案都有人類確認
3. 結案記錄有完整的 `Resolved-By` 追蹤

### Q：pr-review 的 TD Closure Verification 失敗會阻擋 PR 嗎？

不會。這是 SHOULD 層級的驗證，以 WARNING / INFO 形式呈現，不影響 PR 通過與否。它的目的是提醒團隊確認 TD 狀態的一致性。

### Q：舊專案的 technical-debt.md 沒有新欄位怎麼辦？

新增欄位（`Resolved-By`、`Resolved-Date`、`Won't-Fix-Reason`）皆為選填，向後相容。現有的 Register / Dedup 機制完全不受影響。

### Q：哪些問題不應該進 TD？

- **E1 HIGH / CRITICAL / HIGH** → MUST 當場修復，不進 TD
- **Feature 範圍內可修復的問題** → 直接修復，不進 TD
- **純粹的討論或提案** → 走 `docs/02.規則研討/` 或 Issue Tracker
