# Issue 提案處理指南（範本維護者用）

> **版本**：v1.0.0  
> **最後更新**：2026-02-25  
> **適用對象**：範本維護者（人類 + AI Agent）  
> **目的**：標準化 Issue 審閱、決策與實作流程

---

## 1. 概述

當下游專案或協作者提交 Issue 到上游範本 Repo 時，維護者需依據本指南進行審閱、決策與實作。

### 1.1 快速處理口令

對 AI 說：

> 「請依照 `docs/01.開發人員doc/07.Issue提案處理指南.md` 處理 Issue #N」

AI 將自動執行完整的 Issue 審閱 → 決策 → 實作流程。

---

## 2. Issue 審閱流程

### 2.1 Step 1：讀取 Issue

```bash
# 使用 GitHub CLI 讀取 Issue（Private Repo 不可用 URL 讀取）
gh issue view <ISSUE_NUMBER>
```

> ⚠️ 若 Issue 引用了外部私人 Repo 的文件，AI MUST 忽略該引用並僅基於 Issue 主體內容決策。

### 2.2 Step 2：Issue 品質檢查

| 檢查項 | 通過條件 | 未通過處理 |
|--------|----------|-----------|
| 自包含性 | Issue 主體包含完整提案，不依賴外部私人連結 | 回覆請求補充 |
| 清晰度 | 問題描述、建議方案、影響範圍皆明確 | 回覆請求釐清 |
| 可行性 | 提案在技術上可行，不違反 SDD 核心原則 | 說明不可行原因 |
| 通用性 | 提案對多個下游專案有價值（非專案特化） | 建議在下游自行處理 |

### 2.3 Step 3：影響範圍分析

AI MUST 分析提案會影響哪些檔案類別：

| 類別 | 說明 | 風險等級 |
|------|------|----------|
| Agent / Command 指令 | `.github/agents/`、`.cursor/commands/` | 🟡 中 |
| Constitution | `.specify/memory/constitution.md` | 🔴 高 |
| Template 範本 | `.specify/templates/` | 🟡 中 |
| Documentation 文件 | `docs/` | 🟢 低 |
| FlowKit 範本 | `.flowkit/templates/` | 🟡 中 |

---

## 3. 決策框架

### 3.1 決策矩陣

| 決策 | 條件 | 動作 |
|------|------|------|
| **接受（Accept）** | 品質通過 + 通用性高 + 風險可控 | 直接實作 |
| **接受並修改（Accept w/ Modifications）** | 核心想法好但實作細節需調整 | 調整後實作 |
| **延遲（Defer）** | 好提案但目前不急迫 | 標記 `enhancement` + 排入未來 |
| **拒絕（Reject）** | 不符合 SDD 原則或不具通用性 | 說明原因並關閉 |

### 3.2 AI 決策原則

作為 AI 開發長，決策時 MUST 考量：

1. **SDD 一致性**：提案是否符合 Constitution 核心原則？
2. **跨專案影響**：修改會影響所有下游專案，MUST 確保向後相容
3. **最小變更原則**：用最小的修改達到最大的效果
4. **文件同步**：每個修改 MUST 同步更新相關文件和版號

---

## 4. 實作流程

### 4.1 接受後的實作步驟

```
1. 修改指令化檔案（Agent + Command 同步）
2. 更新 Constitution（若涉及）
3. 更新 Template（若涉及）
4. 更新 version-manifest.md
5. 更新改版歷史（docs/76.改版歷史/）
6. 更新 SpecKit 差異說明（若涉及 SpecKit 指令）
7. Git commit + push
8. 在 Issue 回覆實作摘要並關閉
```

### 4.2 Agent + Command 同步規則 🔴 CRITICAL

所有指令化修改 MUST 同時套用到：
- `.github/agents/<指令名>.agent.md`（GitHub Copilot）
- `.cursor/commands/<指令名>.md`（Cursor）

兩邊邏輯 MUST 一致，僅步驟編號可能因格式差異而不同。

### 4.3 Issue 回覆模板

```markdown
## Issue #N 處理結果

**決策**：✅ 接受（/ ✅ 接受並修改 / ⏳ 延遲 / ❌ 拒絕）

### 修改摘要

| 修改檔案 | 變更說明 |
|----------|----------|
| `xxx.agent.md` | ... |
| `xxx.md` | ... |

### 版號更新

| 指令 | 舊版本 | 新版本 |
|------|--------|--------|
| `speckit.implement` | 1.4.0 | 1.5.0 |

### 對應 Commit

`abc1234` — <commit message>

### 下游專案影響

- 下游專案可透過跨範本同步流程取得此更新
- 版號差異可透過 `.flowkit/version-manifest.md` 比對
```

## 5. 常見情境處理

### 5.1 提案引用私人 Repo 文件

- AI MUST 忽略無法存取的外部連結
- 在 Issue 回覆中提醒：「未來提案請將完整內容置於 Issue 主體中」
- 基於 Issue 主體可見內容進行決策

### 5.2 提案涉及 Constitution 修改

- Constitution 修改為高風險操作
- AI SHOULD 先提出修改提案讓人類審閱
- 除非人類明確指示「直接執行」，否則 MUST 等待確認

### 5.3 提案需要大規模重構

- 涉及 3 個以上指令的修改，SHOULD 先提出影響分析
- 列出所有受影響的檔案與修改範圍
- 獲得人類確認後再執行

### 5.4 同一 Issue 包含多個提案

- 建議拆分為獨立 Issue
- 若人類要求一次處理，MUST 逐一評估每個子提案

---

## 6. 品質檢查清單

每次 Issue 處理完成後：

- [ ] Agent 和 Command 版本一致
- [ ] `version-manifest.md` 已更新
- [ ] 改版歷史已記錄
- [ ] 相關功能說明文件已更新（若適用）
- [ ] SpecKit 差異說明已更新（若涉及 SpecKit 指令）
- [ ] Git commit + push 完成
- [ ] Issue 已回覆並關閉（或標記）

---

> **備註**：本指南旨在讓「一句口令就能處理新 Issue」成為可能。  
> AI Agent 閱讀本指南後，可自主完成從審閱到實作的完整流程。
