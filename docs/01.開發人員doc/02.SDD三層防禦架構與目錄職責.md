# SDD 三層防禦架構與目錄職責

> **版本**：v1.0.0  
> **最後更新**：2026-01-31  
> **核心精神**：系統只有一個真相，就是 `specs/system/spec.md`。所有的開發都是為了更新這個真相，而不是繞過它。

---

## 1. 為什麼需要三層防禦？

在 AI 輔助開發的時代，最大的風險是 **AI 隨意修改程式碼導致與原始設計脫鉤**。

| 風險 | 後果 | 防禦方式 |
|------|------|----------|
| AI 產生幻覺 | 實作偏離需求 | 規格約束 AI 行為 |
| 多人協作衝突 | 文件與程式碼不一致 | 唯一真相來源 |
| 無意間破壞架構 | 系統難以維護 | 多層檢查點攔截 |

**核心原則**：

```
┌─────────────────────────────────────────────────────────────┐
│  規格即真相 → AI 依規格行動 → 實作必須符合規格              │
└─────────────────────────────────────────────────────────────┘
```

│  │                                                                  │  │
│  │ • SpecKit 工具運作時的「法律」                                   │  │
│  │ • 定義目錄結構、User Story 格式 (BDD)                           │  │

### 2.1 第一層：全域防護 (copilot-instructions.md)

| 面向 | 說明 |
|------|------|
| **檔案位置** | `.github/copilot-instructions.md` |
| **生效範圍** | VS Code 開啟 Copilot Agent 即生效 |
| **主要職責** | AI 行為的全域約束 |

**核心規則**：

| 規則類型 | 說明 |
|----------|------|
| `NEVER` | 絕對禁止的行為（如：直接修改 `specs/system/`） |
| `MUST` | 必須遵守的規範（如：不確定時先詢問） |
| `SHOULD` | 建議遵守的最佳實踐 |

**關鍵條款**：

```markdown
NEVER 修改 specs/system/**，
除非指令中明確指出正在執行 UNIFY FLOW
```

### 2.2 第二層：專案憲法 (constitution.md)

| 面向 | 說明 |
|------|------|
| **檔案位置** | `.specify/memory/constitution.md` |
| **生效範圍** | SpecKit 指令執行時注入 |
| **主要職責** | 定義規格結構與流程規範 |

**核心規則**：

| 規範 | 說明 |
|------|------|
| 雙層結構 | System (現狀) vs Feature (變更) |
| BDD 格式 | User Story 必須遵循 As a / I want / So that |
| 唯一真相 | `specs/system/` 是系統行為的唯一權威 |

### 2.3 第三層：Unify Flow（合併儀式）

| 面向 | 說明 |
|------|------|
| **觸發時機** | Feature 開發完成、準備發 PR 前 |
| **執行指令** | `/flowkit.unify-flow` |
| **主要職責** | 將 Feature 變更合法化至 System |

**合併原則**：

1. **System Spec 是基底**，Feature Spec 是更新包
2. **衝突時以 Feature Spec 為準**（代表最新設計意圖）
3. 完成後，Feature 目錄會被移到 `specs/history/` 封存

## 3. 目錄結構與職責

### 3.1 核心目錄地圖

```
專案根目錄/
├── .github/
│   └── copilot-instructions.md   🟥 第一層防護
│
├── .specify/
│   └── memory/
│       └── constitution.md        🟨 第二層防護
│
├── specs/                         📋 規格層
│   ├── system/                    🔴 唯一真相（現狀）
│   │   ├── spec.md               ← 系統行為定義
│   │   ├── data-model.md         ← 資料模型
│   │   ├── flows.md              ← 流程設計
│   │   ├── contracts/            ← 介面契約
│   │   └── ui/                   ← UI 設計
│   │
│   ├── features/                  🟡 開發中（變更）
│   │   └── NNN-feature-name/
│   │       ├── spec.md           ← Feature 規格
│   │       ├── plan.md           ← 實作計畫
│   │       └── tasks.md          ← 任務清單
│   │
│   └── history/                   🟤 已封存（唯讀）
│       └── NNN-feature-name/     ← 歷史記錄
│
├── docs/                          📚 參考資料
│   └── requirements/             ← PRD、User Stories
│
├── src/                           💻 程式碼
│   └── ...                       ← 依 specs 實作
│
└── tests/                         🧪 測試
    └── ...                       ← 依 specs 驗證
```

### 3.2 職責與權限一覽

| 目錄 | 狀態 | 說明 | 能改嗎？ |
|------|------|------|----------|
| `specs/system/` | 🔴 **唯一真相** | 代表系統「現在」的行為與設計 | ❌ NO（除非 Unify Flow） |
| `specs/features/` | 🟡 **開發中** | 代表「這次」要改什麼 | ✅ YES（這是你的工作區） |
| `specs/history/` | 🟤 **已封存** | 已合併的歷史記錄 | ❌ NO（唯讀） |
| `docs/` | 🟢 **參考資料** | PRD、User Story、規劃文件 | ✅ YES（僅供參考） |
| `src/` | 🔵 **實作** | 程式碼必須符合 specs 描述 | ✅ YES（測試通過後） |
| `tests/` | 🧪 **測試** | 依 specs 驗證行為 | ✅ YES |

## 4. 規格調整情境指南

### 4.1 情境 A：開發中 Debug（Feature 分支）

| 情況 | 處理方式 |
|------|----------|
| **實作寫錯** | 👉 只改程式碼 |
| **Spec 寫錯/漏寫** | 👉 先改 Feature Spec，再改程式碼 |

🔴 **絕對禁止**：直接去改 `specs/system/`

### 4.2 情境 B：開發中想加功能

| 類型 | 判斷標準 | 處理方式 |
|------|----------|----------|
| **自然演化** | 補充細節 / 修正描述 | 👉 修改當前 Feature 的 `spec.md` |
| **需求擴張** | 新增 User Goal / 影響其他模組 | 👉 **停！** 開新 Feature (`/speckit.specify`) |

### 4.3 情境 C：Main 分支發現 Bug（Hotfix）

| Bug 類型 | 分支命名 | 需要 Feature 目錄？ |
|----------|----------|---------------------|
| **實作 Bug**（Code 錯，Spec 對） | `fix/xxx` | ❌ 不用（直接修 Code 發 PR） |
| **規格 Bug**（Spec 定義就有誤） | `hotfix/xxx` | ✅ **要**（需建 Feature 並跑 Unify Flow） |

## 5. UI 行為同步特別條款

> 🔑 **核心原則**：UI 行為變更 = 規格變更，不得僅改程式碼。

| 階段 | 規則 |
|------|------|
| **開發中** | 允許 UI 邊做邊修，但整合前 MUST 把最終行為回填至 Feature Spec |
| **Debug 時** | 若 UI 需要調整，必須修改 Feature Spec（不是 System Spec） |
| **Unify Flow** | UI 行為 → `spec.md`；UI 結構 → `data-model.md` 或 `flows.md` |

## 6. 快速檢查清單

### 6.1 開發中自我檢查

- [ ] 我是否在 Feature 分支上工作？
- [ ] 我是否只修改 `specs/features/NNN-xxx/` 下的規格？
- [ ] 我的程式碼是否符合 Feature Spec 的描述？

### 6.2 發 PR 前檢查

- [ ] 已執行 `/flowkit.pre-unify-check` 且全數通過
- [ ] 已執行 `/flowkit.unify-flow` 合併至 System
- [ ] 測試全部通過

---

## 7. 懶人包總結 (TL;DR)

| 問題 | 解法 |
|------|------|
| **Copilot 不乖？** | 檢查 `.github/copilot-instructions.md` |
| **UI 改了？** | 記得回填 Feature Spec，不要只改 Code |
| **想加功能？** | 範圍太大就開新 Feature，不要偷渡 |
| **發 PR 前？** | 務必執行 Unify Flow |
| **不確定能不能改？** | 看職責表，🔴 是禁區 |
