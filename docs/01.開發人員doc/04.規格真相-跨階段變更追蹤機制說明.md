> **文件類型**：開發團隊技術說明  
> **版本**：v1.0.0  
> **日期**：2025-07-15  
> **作者**：AI 開發長（AI CDO）  
> **適用範圍**：SpecKit / FlowKit 全流程

---

## 1. 為什麼需要這個機制？

### 1.1 問題背景

在 SDD（Specification-Driven Development）流程中，Feature Spec（`spec.md`）是行為的唯一真相來源。但在實際開發過程中，spec 的內容會在多個階段被合理地修改：

- `clarify`：需求澄清後發現原始 US/AC 需要調整
- `analyze`：靜態分析發現技術限制，建議修改 AC
- `implement`：實作中發現 spec 與實際情況有落差
- `refine-loop`：實作後發現需求需要微調

**核心問題**：到了 `requirement-sync`（需求回寫）階段時，AI 需要判斷「spec 與 PRD/User Stories 的差異」是**刻意修正**還是**非意圖的錯誤**。如果沒有變更追蹤機制，AI 只能猜測——這違反了我們「不猜測」的治理原則。

### 1.2 設計目標

```
讓每一筆 spec 變更都有跡可循，
讓 requirement-sync 能可靠地判斷變更意圖，
讓 pre-unify-check 能偵測到遺漏的追蹤。
```

## 2. 雙層追蹤架構（Two-Tier Tracking）

我們採用雙層機制，各有不同的職責與粒度：

```
┌─────────────────────────────────────────────────────┐
│  Tier 1：Auto-Marking（標題標記）                     │
│  ┌───────────────────────────────────────────────┐  │
│  │  直接在 spec.md 的 US/AC 標題上                │  │
│  │  加上 [MODIFIED] / [NEW] / [DELETED] 標記     │  │
│  │                                               │  │
│  │  適用：clarify、analyze、refine-loop          │  │
│  │  （直接修改 spec.md 的階段）                   │  │
│  └───────────────────────────────────────────────┘  │
│                                                     │
│  Tier 2：Spec Delta Log（規格差異日誌）                    │
│  ┌───────────────────────────────────────────────┐  │
│  │  獨立檔案 FEATURE_DIR/spec-delta-log.md        │  │
│  │  統一 Schema：ID / Stage / Phase / Type /     │  │
│  │  Original / Actual / Impact / Action          │  │
│  │                                               │  │
│  │  適用：所有階段（clarify ~ code-check）        │  │
│  │  （包含不修改 spec 的階段，如 implement）      │  │
│  └───────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────┘
```

### 為什麼是雙層？

| 層級 | 優點 | 限制 |
|------|------|------|
| Tier 1 Auto-Marking | 直覺、低成本、requirement-sync 首選信號 | 只能標記 spec 修改者 |
| Tier 2 Spec Delta Log | 跨階段、結構化、可追溯完整歷程 | 需額外維護檔案 |

兩者互補：Tier 1 是「快速信號」，Tier 2 是「完整記錄」。

## 3. 各階段行為一覽

### 3.1 總覽矩陣

```
階段             Tier 1          Tier 2          說明
                 Auto-Marking    Spec Delta Log
─────────────────────────────────────────────────────────
specify          —               —               初始建立，無變更
clarify          ✅ MUST          ✅ SHOULD        直接修改 spec → 標記
analyze          ✅ MUST          ✅ SHOULD        建議修改 AC → 標記
plan             —               ✅ MAY           不修改 spec
implement        —               ✅ MUST          發現規格差異必須記錄
refine-loop      ✅ 已有機制       ✅ SHOULD        Phase 3/8 delta
code-check       —               ✅ MAY           驗證層，通常無規格差異
consistency-     —               ✅ MAY           唯讀檢查，發現歸報告
  check
```

### 3.2 各階段詳細說明

#### 🔵 clarify（需求澄清）

**角色**：與使用者互動，澄清模糊需求，並**直接更新 spec.md**。

**Tier 1 — Auto-Marking（§8.5 / §7.5）**：
```
在完成 spec.md 寫入後，MUST 自動執行：

1. 比對修改前後的 spec.md
2. 對任何被修改的 US/AC 標題，注入變更標記：
   - [MODIFIED]：既有 US/AC 被修改
   - [NEW]：新增 US/AC
   - [DELETED]：刪除 US/AC

範例：
### US A-1: 使用者登入 [MODIFIED]
### US A-3: 密碼重設 [NEW]
```

**Tier 2 — Spec Delta Log（§8.6 / §7.6）**：
```
SHOULD 將重大變更記錄到 FEATURE_DIR/spec-delta-log.md
Stage 欄位填 "clarify"
```

**為什麼 clarify 需要雙層？**  
因為 clarify 是**最大的追蹤缺口**——它直接修改 spec 卻在本次改版前完全沒有標記機制。

---

#### 🔵 analyze（靜態分析）

**角色**：分析 spec 的可行性，識別技術風險。在 Remediation 階段可修改 spec.md。

**Tier 1 — Auto-Marking（§9.5，已於 v1.3.0 實作）**：
```
當 Remediation 修正 spec.md 中的 US/AC 時，
MUST 在修正項目的標題加上 [MODIFIED] / [NEW] / [DELETED]
```

**Tier 2 — Spec Delta Log（§9.6，已於 v1.3.0 實作）**：
```
SHOULD 將 Remediation 記錄寫入 spec-delta-log.md
Stage 欄位填 "analyze"
```

---

#### 🔵 implement（實作執行）

**角色**：按照 tasks.md 實作程式碼。**MUST NOT 修改 spec.md**。

**Git Hash 基線（§1.5）**：
```
在開始實作前，MUST 記錄當前 git commit hash 到 spec.md YAML frontmatter：

---
implement_baseline_commit: "abc1234"
---

此基線供 pre-unify-check 做 git diff 比對。
```

**Tier 2 — Spec Delta Log（§10.5 / §8.5，MUST）**：
```
實作過程中發現 spec/plan/tasks 與實際不一致時，
MUST 記錄到 spec-delta-log.md（不中斷實作流程）。

Stage 欄位固定填 "implement"。
MUST NOT 修改 spec.md（SDD 原則），規格差異由後續 refine-loop 處理。
```

**為什麼 implement 是 MUST？**  
因為 implement 是最常發現「spec 與現實落差」的階段。如果不記錄，這些資訊會遺失，導致 refine-loop 和 requirement-sync 無法正確判斷。

---

#### 🔵 refine-loop（實作後調整）

**角色**：修正 implement 中發現的問題，可修改 spec.md。

**已有機制**（Phase 3 產生 delta、Phase 8 合併後移除標記）：
```
Phase 3：產生 refine-spec-delta.md（結構化變更記錄）
Phase 8：合併完成後移除 [MODIFIED] 標記
```

refine-loop 是最早擁有追蹤機制的階段，本次改版不需額外修改。

---

#### 🟡 pre-unify-check（Unify 前品質檢查）

**角色**：在 Unify Flow 前驗證文件品質。**唯讀**，不修改任何檔案。

**新增 §3.5 Spec Delta Log 交叉比對**：
```
觸發條件：spec.md YAML 存在 implement_baseline_commit

步驟：
1. git diff <baseline>..HEAD -- FEATURE_DIR/
2. 解析 spec.md 變更行 → 識別被修改的 US/AC
3. 交叉比對 spec-delta-log.md
4. 結果分類：

  spec 變更有對應 spec-delta-log  → ✅ OK
  spec 變更有 [MODIFIED] 但無 log → ⚠️ LOW（建議補充）
  spec 變更無標記也無 log       → ⚠️ MEDIUM（可能為未追蹤變更）
  spec-delta-log 有記錄但 spec 無 → ℹ️ INFO（可能已由 refine-loop 處理）
```

---

#### 🟡 requirement-sync（需求回寫）

**角色**：將 Feature Spec 的變更回寫到 PRD 和 User Stories。

**使用所有信號源**：
```
信號源優先順序（Phase 0.1 掃描 + Phase 3 判斷）：

1. [MODIFIED] 標記         → 最強信號，直接判為「刻意修正」
2. plan.md 變更說明         → 次強信號
3. refine-spec-delta.md    → refine-loop 產生的記錄
4. spec-delta-log.md        → 跨階段規格差異日誌（新增）
5. 內容差異分析             → 兜底判斷
```

**判斷邏輯（更新後）**：
```
FOR each difference:
  IF [MODIFIED] 標記        → 刻意修正（自動回寫）
  ELSE IF Plan 有說明       → 刻意修正
  ELSE IF refine-delta 有   → 刻意修正
  ELSE IF spec-delta-log 有  → 刻意修正（新增！）
  ELSE IF 更詳細而非不同    → 澄清補充（建議回寫）
  ELSE IF 純格式差異        → 忽略
  ELSE                      → 非意圖不一致（詢問使用者）
```

## 4. Spec Delta Log Schema

```markdown
## Spec Delta Log

| ID | Stage | Phase | Type | Original (spec/plan) | Actual/Discovery | Impact | Action |
|----|-------|-------|------|---------------------|-----------------|--------|--------|
| D1 | implement | Phase 2 | 技術限制 | spec: 即時同步 | API 僅支援輪詢 | US-A-2 AC1 | 待 refine-loop |
| D2 | clarify | Step 5 | 需求變更 | US-B-1: 舊標題 | US-B-1: 新標題 | US-B-1 | 已更新 spec |
| D3 | analyze | §8 | 可行性 | AC: 100ms 回應 | 預估 500ms+ | US-C-1 AC3 | 建議調整 |
```

**欄位說明**：

| 欄位 | 說明 |
|------|------|
| ID | 流水編號 D1, D2, D3... |
| Stage | 產生此規格差異的階段（clarify / analyze / implement / ...） |
| Phase | 該階段中的具體步驟或 Phase |
| Type | 規格差異類型（技術限制 / 需求變更 / 可行性 / 架構調整 / ...） |
| Original | 原始 spec/plan 的描述 |
| Actual/Discovery | 實際發現或調整後的內容 |
| Impact | 影響的 US/AC 編號 |
| Action | 處理方式（已更新 spec / 待 refine-loop / 建議調整 / ...） |

## 5. 生命週期圖

```
specify ──→ clarify ──→ analyze ──→ plan ──→ implement ──→ refine-loop
                │            │                    │            │
                ▼            ▼                    ▼            ▼
           Tier1+Tier2  Tier1+Tier2          Tier2(MUST)  Tier1+Tier2
                │            │                    │            │
                └────────────┴────────────────────┴────────────┘
                                      │
                                      ▼
                              spec-delta-log.md
                              [MODIFIED] 標記
                                      │
                    ┌─────────────────┼─────────────────┐
                    ▼                 ▼                  ▼
             pre-unify-check   requirement-sync    unify-flow
                        (git diff 比對)   (意圖判斷用)       (Feature Summary)
             (spec-delta-log    (多信號源判斷)     (品質指標萃取)
              交叉驗證)
```

### 標記生命週期

```
[MODIFIED] 標記產生                    [MODIFIED] 標記移除
         ↓                                    ↓
  clarify 注入                         Unify Flow Phase 完成
  analyze 注入                         refine-loop Phase 8
  refine-loop Phase 3 注入
         ↓
    requirement-sync 使用（判斷意圖）
    pre-unify-check 使用（品質檢查）
         ↓
  Unify Flow 完成後，spec.md 中
  不得殘留變更標記
```

## 6. 常見問題

### Q1：如果 clarify 忘記加 [MODIFIED] 標記怎麼辦？

不會忘記——這是 **MUST** 等級的自動行為。AI 在完成 spec 寫入後，會自動比對修改前後差異並注入標記。如果真的漏了，`pre-unify-check` 的 §3.5 git diff 交叉比對會偵測到「spec 有變更但無標記」，發出 ⚠️ MEDIUM 警告。

### Q2：implement 發現規格差異但不能改 spec，那怎麼處理？

記錄到 `spec-delta-log.md` 後繼續實作。規格差異會在後續 `refine-loop` 中被處理——refine-loop 可以修改 spec.md 並加上 `[MODIFIED]` 標記。這樣做的好處是保持 SDD「spec 是真相」的原則不被實作階段破壞。

### Q3：spec-delta-log.md 是必須建立的嗎？

不一定。如果整個 Feature 開發過程中沒有任何規格差異（spec 完全正確、實作完全順利），就不需要建立這個檔案。只有 `implement` 階段是 MUST——如果發現規格差異就必須記錄。其他階段是 SHOULD 或 MAY。

### Q4：Feature Summary 有什麼用？

Feature Summary 儲存在 `.flowkit/memory/learning/feature-summaries/` 目錄下，是每個 Feature 完成後的經驗總結。目前是 Phase A（自動產生），未來 Phase B 會讓 `plan` 階段讀取歷史 Summary，提升工時預估準確度。

### Q5：這和 refine-spec-delta.md 有什麼不同？

| 項目 | refine-spec-delta.md | spec-delta-log.md |
|------|---------------------|-----------------|
| 產生階段 | 僅 refine-loop | 所有階段 |
| 內容 | spec.md 的具體 diff | 結構化規格差異記錄 |
| 格式 | 自由格式 | 統一 Schema |
| 生命週期 | refine-loop 內部 | Feature 全週期 |

兩者互補，`requirement-sync` 會同時使用兩者。
