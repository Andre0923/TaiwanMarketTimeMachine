# 測試策略與自動化機制

> **版本**：v1.0.0  
> **最後更新**：2026-02-15  
> **適用對象**：新進開發人員、AI Agent  
> **相關指令**：`speckit.implement`、`flowkit.code-check`、`flowkit.refine-loop`

---

## 1. 總覽

本專案採用 **Test-First（測試優先）** 開發紀律，搭配 **自動化測試分批執行** 與 **慢測試自動標記** 機制，確保測試品質與執行效率兼顧。

### 1.1 核心理念

```
AC（驗收條件）→ 衍生測試 → tests/ 新增 → src/ 修改 → code-check 驗證
```

> 📌 **NON-NEGOTIABLE**：測試 MUST 先於程式碼修改（copilot-instructions §5、constitution §3.1）

### 1.2 測試技術棧

| 項目 | 工具 | 說明 |
|------|------|------|
| 測試框架 | pytest | `--strict-markers`、`--verbose` |
| 覆蓋率 | pytest-cov | 報告至 `.artifacts/coverage/` |
| 慢測試標記 | `@pytest.mark.slow` | 自動標記 + 手動標記 |

## 2. 測試流程全景

### 2.1 測試在 SDD 流程中的位置

```
specify → plan → tasks → analyze → implement → code-check → pre-unify-check
                                       │              │
                                       │              ├─ L2: 測試 + 回歸分析
                                       │              │     └─ 串行執行全部測試
                                       │              │
                                  Test-First          └─ FAIL → refine-loop → 重跑
                                  撰寫測試
```

### 2.2 各階段的測試職責

| 階段 | 指令 | 測試相關職責 |
|------|------|-------------|
| 規格定義 | `speckit.specify` | AC 撰寫（Given/When/Then），可直接轉測試 |
| 技術規劃 | `speckit.plan` | Constitution §3.1 TDD 合規檢查、Test Strategy 規劃 |
| 任務拆解 | `speckit.tasks` | 測試任務（Optional，需明確要求）、`[US*]` 標籤供追溯 |
| 實作 | `speckit.implement` | **Test-First**：先寫測試 → 再寫程式碼；標記 `@pytest.mark.slow` / `serial` |
| 驗證 | `flowkit.code-check` | L2 自動執行測試套件（並行分批）、回歸分析、Flake Detection |
| 修正 | `flowkit.refine-loop` | 以 Test-First 修正 Bug、測試保護重構行為 |
| 合併前 | `flowkit.pre-unify-check` | AC 可測試性檢查、AC↔測試覆蓋率驗證 |
| 健康檢查 | `flowkit.system-health` | 測試通過率評分、AC↔測試覆蓋度評分 |

## 3. 測試標記系統

### 3.1 標記種類

| 標記 | 用途 | 自動化 | 判斷準則 |
|------|------|--------|----------|
| `@pytest.mark.slow` | 耗時測試 | ✅ 支援自動標記 | 執行超過 30 秒（外部程式呼叫、大量資料處理、網路請求） |
| `@pytest.mark.serial` | 不可並行測試 | ❌ 僅手動 | 使用共享資源（DB、檔案 I/O、網路 port、全域狀態） |

### 3.2 `@pytest.mark.slow` 自動標記機制

conftest.py 透過 `pytest_collection_modifyitems` hook 實現自動標記：

```
第一次執行 → 無歷史 → 全部一起跑 → 耗時記錄至 .artifacts/test-durations.json
                                              │
第二次起  → conftest 讀歷史 ─────────────────┘
           → 超過 SLOW_THRESHOLD_SECONDS (30s) 自動加 @pytest.mark.slow
           → code-check 分批策略自動生效
           → 手動標記的 @pytest.mark.slow 仍然優先

每次執行都會更新 test-durations.json
→ 測試越跑越準確
→ 效能改善後自動移除慢標記
```

### 3.3 `@pytest.mark.serial` 判斷準則

**MUST 標記 `@pytest.mark.serial` 的情境**：

| # | 情境 | 原因 |
|---|------|------|
| 1 | 共享資料庫 | 多個測試讀寫同一個 DB（非 in-memory） |
| 2 | 共享檔案 | 多個測試讀寫同一個檔案或目錄（非 `tmp_path`） |
| 3 | 網路 port | 測試啟動 server 並綁定固定 port |
| 4 | 全域狀態 | 修改環境變數、單例模式、全域設定 |
| 5 | 外部服務互斥 | 呼叫同一個外部 API 且有 rate limit |

**不需要標記的情境**（可安全並行）：

- 使用 `tmp_path` fixture（pytest 自動隨機化）
- 使用 in-memory SQLite
- 各測試獨立建立自己的資源
- 純函式計算 / 轉換測試

### 3.4 範例

```python
import pytest

# 純計算函式 → 不需任何標記，可安全並行
def test_calculate_moving_average(sample_data):
    result = calculate_ma(sample_data, period=20)
    assert len(result) == len(sample_data) - 19


# 呼叫外部程式 → 自動標記 @pytest.mark.slow（第二次起生效）
# 也可手動預先標記
@pytest.mark.slow
def test_process_large_audio_file(sample_audio):
    """處理大檔音訊，耗時超過 30 秒。"""
    result = transcribe(sample_audio)
    assert result.text != ""


# 使用共享 DB → MUST 手動標記 @pytest.mark.serial
@pytest.mark.serial
def test_write_to_shared_db(db_connection):
    """寫入共享 DB，不可並行。"""
    db_connection.insert({"key": "value"})
    assert db_connection.count() == 1


# 既慢又用共享資源 → 雙標記
@pytest.mark.slow
@pytest.mark.serial
def test_external_api_heavy(api_client):
    """呼叫外部 API，既慢且有 rate limit。"""
    response = api_client.batch_request(items=1000)
    assert response.status == "ok"
```

## 4. 測試執行策略

### 4.1 code-check L2 執行策略

`flowkit.code-check` 的 Phase 2（L2 Unit Tests）使用串行執行：

```
uv run pytest tests/ -q --tb=short
```

> 註：conftest.py 會自動根據 `.artifacts/test-durations.json` 歷史耗時識別慢測試候選並回報，供開發者參考。

### 4.2 回歸分析

code-check 執行回歸分析三步法：

1. **基線載入**：讀取 `.artifacts/test-failures-baseline.txt`
2. **失敗比對**：本次失敗 vs 基線
3. **Feature 關鍵字 grep**：新增失敗是否匹配 Feature 關鍵字

| 結果 | 判定 |
|------|------|
| 新增失敗 = 0 | ✅ PASS |
| 新增失敗 + 不匹配關鍵字 | 🟡 CONDITIONAL → 進入非功能回歸分流 |
| 新增失敗 + 匹配關鍵字 | ❌ FAIL（Feature 回歸） |

### 4.3 非功能回歸分流（Bug-Fix Triage）

當測試失敗不匹配 Feature 關鍵字時，code-check 會自動分類與分流：

1. **失敗分類**：FIXTURE-POLLUTION / TEST-DATA / API-CHANGE / ENV-TOOL
2. **成本評估**：EASY / MEDIUM / HIGH
3. **分流決策**：
   - EASY/MEDIUM 且不需改 spec → 產出 `.artifacts/bug-fix-list-feature-<NNN>.md`，自動 handoff 至 refine-loop
   - HIGH 或需改 spec → 登記為 TD

> 此機制避免 EASY/MEDIUM 的純 bug-fix 問題累積成 TD，在當下由 refine-loop 的 Bug-Fix 模式自動修復。

### 4.4 Flake Detection

新增失敗在判定 FAIL 前，自動重跑一次：
- 第二次通過 → flake suspicion → 🟡 CONDITIONAL + Escalation
- 第二次仍失敗 → 照原判定邏輯

### 4.5 system-health 測試健康度

`flowkit.system-health` 的 D1 維度評估全專案測試健康度：

| 通過率 | 評分 |
|--------|------|
| ≥ 95% | 100 分 |
| ≥ 85% | 80 分 |
| ≥ 70% | 60 分 |
| ≥ 50% | 40 分 |
| < 50% | 20 分 |

## 5. 測試產物與目錄

### 5.1 目錄結構

```
tests/                           # 測試檔案（MUST 放在此目錄）
├── conftest.py                  # 共用 Fixtures、Marker 註冊、自動標記
├── test_*.py                    # 測試檔案（命名規則）
└── __init__.py

.artifacts/                      # 測試產物（MUST 被 .gitignore 排除）
├── pytest_cache/                # pytest 快取
├── coverage/
│   ├── .coverage                # coverage 資料
│   ├── html/                    # HTML 報告
│   └── coverage.xml            # XML 報告
├── test-durations.json          # 各測試耗時記錄（conftest.py 自動產生）
├── test-failures-baseline.txt   # 回歸基線（code-check 產生）
├── test-failures-current.txt    # 當次失敗清單（code-check 產生）
├── bug-fix-list-feature-*.md    # 非功能回歸 bug-fix 清單（code-check 產生，若有）
└── code-check-report-feature-*.md  # 驗證報告
```

### 5.2 pyproject.toml 設定

```toml
[tool.pytest.ini_options]
testpaths = ["tests"]
python_files = ["test_*.py"]
python_classes = ["Test*"]
python_functions = ["test_*"]
cache_dir = ".artifacts/pytest_cache"
addopts = [
    "--verbose",
    "--strict-markers",        # 未註冊的 marker 會報錯
    "--cov=src",
    "--cov-report=html:.artifacts/coverage/html",
    "--cov-report=xml:.artifacts/coverage/coverage.xml",
    "--cov-report=term-missing",
]

[tool.coverage.run]
data_file = ".artifacts/coverage/.coverage"
```

### 5.3 必備依賴

```toml
# pyproject.toml
dependencies = [
    "pytest>=7.4.0",
    "pytest-cov>=4.1.0",
]
```

## 6. 測試命名與追溯

### 6.1 命名規範

- 測試名稱 SHOULD 標註對應的 US / AC 編號
- 範例：`test_us1_ac1_user_login_success()`

### 6.2 @spec 註解（Traceability）

在 implement 階段，建立新檔案時會加入 `@spec` 註解：

```python
# @spec US1 (NNN-feature-name/spec.md#user-story-1)
# @spec-ac AC1.1, AC1.2

class UserService:
    pass
```

### 6.3 pre-unify-check 覆蓋驗證

pre-unify-check 會檢查：
- **C1**：每個 AC 是否可測試（有明確條件）
- **TR2**：每個 AC 至少有一個對應測試（透過 `@spec-ac` 追溯）

## 7. conftest.py 完整功能

conftest.py 是專案級的測試基礎設施，提供：

| 功能 | 對應 Hook | 說明 |
|------|-----------|------|
| Marker 註冊 | `pytest_configure` | 註冊 `slow` 和 `serial` marker |
| 自動慢測試標記 | `pytest_collection_modifyitems` | 讀取歷史耗時，自動加 `@pytest.mark.slow` |
| 慢測試候選提示 | `pytest_terminal_summary` | 列出超閾值但未標記的新慢測試 |
| 耗時記錄 | `pytest_terminal_summary` | 寫入 `.artifacts/test-durations.json` |
| 自動標記統計 | `pytest_terminal_summary` | 報告本次自動標記的測試數量 |

### 7.1 自訂設定

```python
# tests/conftest.py 中可調整的設定

# 慢測試閾值（秒）— 預設 30 秒
```

## 8. 常見情境 Q&A

### Q：新 Feature 實作時，AI 怎麼知道要標記 `@pytest.mark.serial`？

`speckit.implement` 指令內建 §7.5 測試標記指引，AI 會根據 5 種判斷準則（共享 DB、共享檔案、網路 port、全域狀態、外部服務互斥）判定是否需要標記。

### Q：`@pytest.mark.slow` 需要手動標記嗎？

**通常不需要**。conftest.py 的自動標記機制會在第二次測試執行時，根據歷史耗時自動標記。但如果你 **事前就知道** 某個測試會很慢（如呼叫 ffprobe、處理大檔案），可以預先手動標記。

### Q：如果測試效能改善了，慢標記會自動移除嗎？

**自動標記的會**。因為 conftest.py 每次都從 `test-durations.json` 重新判斷，測試變快後歷史耗時更新，下次就不會被自動標記。手動標記的則需要手動移除。

### Q：code-check FAIL 後怎麼辦？

進入 `flowkit.refine-loop`，以 Test-First 修正問題後，重跑 `flowkit.code-check`。

### Q：code-check 發現非功能回歸（不匹配 Feature 關鍵字的測試失敗）怎麼辦？

code-check 會自動分類與分流：EASY/MEDIUM 成本且不需改 spec 的項目，產出 bug-fix 清單並自動 handoff 至 refine-loop（Bug-Fix 模式）立即修復。HIGH 成本或需改 spec 的項目，則登記為 TD 後續處理。
